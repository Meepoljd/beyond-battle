# 战报之外：产品与技术愿景（讨论稿）

本稿基于仓库的 README、开发计划、实现状态与现有代码整理，并结合本次讨论提出后续方向。原始计划曾完整阅读，但仓库没有经字节校验的原件；本稿不是原文复刻。与 dot 的沟通入口尚未获得，涉及产品取舍的提议仍待 dot 和用户确认。

## 产品目标

玩家扮演指挥官，通过有限、延迟且可能过时的报告理解战场，向具有职责和个性的下属分配任务。下属依自己掌握的信息与被授权的自主权行动；玩家需要判断何时介入、何时信任下属，以及如何处理命令与现场变化之间的差异。演习结束后，同一时间线并列展示实际发生的事、总部当时知道的事，以及各角色为何采取行动。玩家可审阅合作经历，决定哪些内容进入后续演习。

现阶段已有固定守桥场景、规则决策、有限观察、指挥链、通信延迟、战后对照和受限记忆。OpenCode 是新增的可选决策方式；它不改变模拟内核的结算权。长期体验、扩展场景和大规模玩法仍为方向，不能视作已交付。

## 玩家体验

一局从认识队伍与简报开始。玩家选择参演指挥官，了解其职责、倾向和已确认经历；阅读任务、地形、可用资源与通信条件；进入指挥台后，下达带目标、优先级、有效期、自主权和保全条件的任务。命令提交、到达、执行和回执是不同事件。玩家手动推进时间，依据到达总部的报告调整判断。战场不会因为关闭页面或服务器离线自动追赶。

局中地图是情报视图：位置、敌情估计和时间戳反映总部最后知道的情况，不将未送达信息当作实时事实。断联、延迟、命令冲突与失效应能被玩家理解。局后开放完整事实和各角色的决策来源，让玩家看到自己当时为什么会得到不同判断。

当前自由文字在规则模式只作备注；OpenCode 模式可在命令送达后参考文字，但仍须遵守结构化授权、动作和地图校验。任意自然语言命令的完整理解、复杂约束和动态目标均未实现。

## 世界、单位与指挥

规则内核负责时间、地形、视野、通信、移动、冲突、伤害、补给和胜负等战场事实。当前只实现其中的简化子集：区域地图、有限动作、同时结算、弹药消耗、士气和结束条件。复杂补给、俘虏、细粒度地形、动态事件及更完整的指挥层级属于待设计方向。

单位可以有不同职责、性格、经验和风险偏好。角色只能依据自身观察、实际收到的命令、已知报告及获准使用的经历提出行动。对手也应有可解释的目标和局部信息；本次 OpenCode 仅用于友方，敌方仍使用规则。未来是否让敌方使用模型、是否允许角色之间协商或动态编组，需结合成本和可玩性验证。

上级任务可以规定目标、优先级、时限、授权范围和保全条件。越级命令、转达延迟、命令撤销和替换应保留来源与时序。当前实现有简化的越级同步，没有独立上级的完整再决策。模型可以偏离授权的建议，但校验和规则决定提案是否可执行；未经结算的模型叙述不能直接改变真相。

## 情报与通信

同一事件有发生时间、观察时间、发送时间和接收时间。总部、下属和敌方分别拥有不同的知识边界。报告可以延迟、过期、被中断或因静默推迟，但需要在界面标注状态，避免把“无报告”解释为“没有敌人”。角色的估计和事实需要区分，必要时展示置信程度与来源。

当前区域视野和敌情估算较简单，通信采用固定回合窗口，尚未模拟带宽、侦察误报、复杂遮挡或人为欺骗。后续扩展前需要明确可观察范围和重放规则，并验证不会通过普通接口泄露未送达事实。

## 决策与模型

一次回合先投递已到达消息，为每个单位生成有限观察，再收集行动提案。提案经过动作、目标、命令和记忆引用校验，之后统一结算。OpenCode 使用独立、禁止工具的短会话，传入角色身份与该单位观察，返回结构化提案；模型不能直接改库、运行代码或调用其他项目工具。当前敌方仍为规则驱动。

每局固定选用规则或 OpenCode。模型不可用、超时、提案无效或本局请求额度耗尽时，本回合对应角色回退到规则，并在界面提示。请求额度在调用前持久化预留，进程中断也不自动退还；它限制游戏侧提交次数，不保证模型供应商没有内部重试，也不是金额预算。真实部署应另设供应商额度和告警。

当前模型调用在写事务外执行，后台任务保存状态，重试同一请求不会重复提交回合。模型结果、观察及来源记录随已提交回合保存；复盘使用保存的提案，不重新请求模型。当前尚无供应商账单对账、精确金额预留、跨进程队列或完整任务取消。

## 经历、复盘与长期关系

复盘从事件和状态摘要重建，比较事实、当时的总部情报和角色决策；核验失败需明确显示，不能把不一致称为重放成功。长期经历应能追溯到角色实际知道的事件，支持玩家审阅、保留和停用，并限制注入数量。经历影响合作与沟通，不应变成永久兵力、装备或数值奖励。

现有实现只从实际送达的命令中提取一种沟通约定，不做开放式人物总结。未来若扩展关系、信任、角色评价或自动摘要，应先定义证据、冲突处理、过期和删除，再评估是否让玩家可见与可编辑。不会把战后全知事实自动灌给角色。

## 数据、可靠性与服务

现有 SQLite 单进程、单 worker；回合开始与完成分为短事务，任务状态和幂等键支持恢复。重启将未完成任务标为 interrupted，不自动追赶；玩家可以用新请求推进未提交回合。事件、快照和已记录决策提供校验。每局保存场景快照，但旧版本内核路由尚未实现；规则变更需显式版本化并保留可恢复的应用和数据库备份。

面向多人或长期托管前，需要独立用户身份与数据隔离、数据库迁移、访问控制、备份恢复演练、资源限额和监控。当前原型仅供单用户，不能因同源检查而当作公网多用户服务。游戏数据和密钥应有独立存储与生命周期；MyAgent 的 NUC 和代理可作为用户指定的候选部署路径，需核实现网配置、隔离边界、认证和回滚后实施。

## 体验与验收

近期先围绕守桥完成真实设备试玩：玩家是否能理解过时情报、命令状态、自主行动和战后因果；记录卡住的步骤及是否愿意再开一局。对模型模式，应在相同场景对比规则、有效模型提案和回退结果，观察行动是否遵循授权，不能仅以文笔评价。断网、刷新、响应丢失、模型超时和进程重启都应保留最后提交状态。

自动验证覆盖规则 golden fixture、事务和幂等、信息边界、非法模型输出、预算耗尽和回放，浏览器覆盖手机与桌面关键路径。真实模型服务、费用、NUC、公网与手机真机各自独立验收；模拟服务通过不等于真实供应商或线上部署通过。

## 迭代顺序（建议）

1. 完成 OpenCode 接入的真实模型试用，选定供应商、模型和花费上限；让玩家能辨认回退和费用风险。
2. 在独立游戏服务上接入已授权的 NUC 公网路径，先检查现有代理及认证，再做真机验证和备份演练。
3. 组织小范围试玩，优先修复报告可理解性、指挥反馈和回合节奏。
4. 按反馈扩展任务解释、观察和指挥关系；保持规则版本、信息来源和可重放性。
5. 经验证后扩展场景、角色经历与长期关系，再评估更大地图、敌方模型、动态事件和多人能力。

顺序、预算、商业化、付费和具体期限尚未由用户确认，不视为已承诺计划。
